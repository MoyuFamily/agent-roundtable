# Roundtable 产品方向与近期计划

更新：2026-11-10。状态：方向已确认，效果待真实使用验证。

本文定义当前产品方向、能力边界和投入顺序。早期 Sprint PRD、设计稿和发布讨论作为历史资料保留；涉及产品目标与优先级时，以本文为准。

## 定位与起点

**Roundtable 为重要决策组织合适的专业角色，由不同 Agent 和模型承担分析，帮助用户完成跨专业取舍。**

项目最初的需求是让不同角色协助做重要决策和评审，补足单一视角的局限；随后扩展到不同 Agent 和模型，以利用不同的能力、上下文和工具。项目开发后暂缓，未对外推广，因此不能把外部使用数据的缺失视为需求已被否定。

当前优先服务维护者自身及有类似需求的使用者。独立产品、可复用组件或轻量 Skill 的形态，由真实任务中的收益和维护成本决定。现有代码量不构成继续投入的理由，也不要求为了转型重写全部基础设施。

## 要实现的价值

“重要决策”指需要不同专业共同判断，且选择会影响资源投入、后续路径或返工成本的问题。当前场景清单见下表；验证顺序不缩小产品范围。普通事实查询和容易撤销的小选择不需要完整圆桌流程。该范围不代表项目具备覆盖所有专业领域的能力。

| 价值 | 需要回答的问题 |
|---|---|
| 专业视角覆盖 | 这次决策涉及哪些职责？重要角色是否缺席？ |
| 专业分析深度 | 各角色是否提供具体的约束、依据、方案和验证办法？ |
| 跨专业取舍 | 不同角色的要求冲突时，有哪些整体可行的选择？ |
| 决策可追溯 | 推荐依据、未决争议和最终用户选择能否被区分和回查？ |

待验证的产品承诺：用户提出一个重要问题后，可以获得适合该问题的专业团队和可供取舍的方案，减少自己组织、追问和综合多个 Agent 的工作。讨论轮数、模型数量、共识比例和记录长度不作为价值指标。

## 场景清单

以下六类决策与 Code Review 都属于当前产品方向。Code Review 是并列的核心场景，不替代其他决策场景。角色组合是起点，应随问题、实际材料和可用能力调整。

| 场景 | 具体问题 | 可能需要的角色 | 应交付的结果 |
|---|---|---|---|
| 项目去留与方向 | 项目继续维护、转型，还是停止？ | 产品、技术、运营、资源规划 | 继续/调整/停止的比较、投入边界、验证计划和复审条件 |
| 产品范围与优先级 | 先做哪个用户群？哪些功能进入 MVP？ | 产品、设计、开发、运营 | 目标用户、MVP 范围、优先级依据、暂缓项和验收方式 |
| 技术路线 | 自研还是采购？继续现有架构还是迁移？ | 架构、开发、运维、产品 | 方案收益与总成本、依赖、迁移风险、演进和退出路径 |
| 发布与实施 | 当前版本能否上线？采用哪种迁移方案？ | 开发、测试、运维、用户支持 | 上线条件、阻塞项、实施步骤、回滚条件和未验证部分 |
| 资源与商业模式 | 有限预算投在哪里？免费、订阅还是按量收费？ | 产品、经营分析、技术、运营 | 资源分配或收费方案比较、成本/收入假设、敏感条件和试点指标 |
| 工作流程与工具选择 | 是否引入某个工具？收益是否抵得过迁移和维护成本？ | 实际使用者、技术、流程负责人 | 当前流程基线、工具收益、迁移/培训/维护负担和试用退出标准 |
| Code Review | 改动是否符合预期？有何缺陷或维护风险？是否建议合并？ | 正确性、架构与维护性、安全、测试与可靠性 | 带定位和证据的问题清单、阻塞项、未验证部分及合并建议 |

这些场景共用简报、角色任务、独立分析、交叉回应和综合取舍流程，分别约定所需材料与交付物。当前并没有七套已经验收的自动化产品：前六类可以通过通用 `decision-support` 流程调整角色和任务，产品/技术等也有既有模板；Code Review 另有专用模板。通用模板默认的产品、技术、设计、运营角色不应机械套用到资源分配或工具选择。

先选有真实问题和可取得材料的场景做验证，按实际收益安排投入。资源与商业模式需要明确成本、使用量、付费需求等假设；工具选择需要现有流程基线及试用证据。材料不足时标明未知，提出验证行动，不凭模型意见填补事实。

## 角色、Agent、模型的边界

| 对象 | 职责 | 当前安排 |
|---|---|---|
| 角色 | 定义关注问题、责任范围、需要的材料和交付物 | 用户或协调者选择；角色必须结合任务，不固定每次召集同一桌人 |
| Agent | 携带上下文和工具，执行角色任务并回应其他角色 | 由宿主创建或接入，明确实际可用材料和权限 |
| 模型 | 为具体分析任务提供推理与生成能力 | 宿主选择；记录选择理由和实际表现，不固化某品牌对应某职位 |
| 协调者 | 明确问题、组织角色、分配讨论重点、综合取舍 | 在宿主中执行，不代替专业角色编造独立意见 |
| 用户 | 提供目标、偏好与约束，作出最终决定 | 推荐方案与用户已批准的决定分别记录 |

多角色与多模型可以分别使用。只有一个模型时，仍可验证角色覆盖的价值；增加模型应有具体理由，并评估额外成本。角色或模型名称本身不构成专业能力的证明。自动选人、自动模型路由和能力排行榜尚未实现。

## 建议的工作流程

1. **明确决策。** 整理待决定事项、目标、约束、备选方案、已有事实、缺失材料、决策人和时间/成本预算。仅对会影响取舍的信息追问。
2. **组建专业团队。** 为各角色写清职责、所需资料、必须回答的问题和预期交付物；角色数量随任务变化。记录宿主实际使用的 Agent、模型和选择理由，未知信息标为未知。
3. **各自分析。** 先根据共同材料和角色职责形成初步判断。需要独立首轮时，宿主分离上下文；当前提示词可以不附带其他人的发言，但不提供访问隔离。
4. **围绕冲突协作。** 协调者归纳会影响选择的冲突，让相关角色回应约束、补充证据、提出替代方案或分阶段方案。对同一信息的重复表达不增加权重。
5. **形成决策说明。** 比较可行方案的收益、成本和代价，给出有条件的推荐、仍成立的反对意见、未决问题和验证行动。
6. **由用户取舍。** 记录用户选择，或明确尚待决定。信息不足时，交付下一步验证计划；用户要求执行后再进入实施。

阶段是协调者的工作约定，当前数据库仅管理轮次。根据问题覆盖程度、信息增益和预算决定是否继续；达到轮次上限可以结束并保留分歧。业务层会自动推进轮次，协调者不应每轮再次手动 advance。

## 最小交付约定

以下字段目前由协调者组织在 context、发言和 conclusion 的文本中，尚不是新增的持久化数据模型。

### 决策简报

- 待决定事项、决策人和时间。
- 目标、约束、偏好，以及暂不讨论的范围。
- 备选方案，包括维持现状或暂缓（适用时）。
- 已有资料及来源；未知事实和待验证假设。
- 可用 Agent、工具、模型及时间/费用预算。

### 角色任务

- 本角色的责任和边界。
- 必须回答的专业问题与可用材料。
- 预期交付物及需要其他角色回应的约束。
- 实际 Agent/模型安排与选择理由；没有观测到的配置不能猜测。

### 角色分析

- 专业判断与可行选项。
- 依据、来源和不确定性，区分事实、预测和偏好。
- 收益、成本、风险及与其他角色的冲突。
- 会改变判断的条件、待验证事项。
- 回应阶段引用相关发言 ID，说明新增或修订了什么。

### 最终决策说明

- 决策问题、目标和实际覆盖的角色；缺席视角。
- 方案比较：收益、代价、适用条件和依赖。
- 推荐方案及理由，引用支持它的原始发言或资料。
- 保留的分歧、未验证假设、信息缺口及其影响。
- 验证或实施行动、建议负责人、触发复审的条件。
- 决策状态：建议待用户决定／用户已确认／暂缓待验证。用户未指定或确认的负责人只能标为建议。

## 一个示例

问题：个人用户产品是否应该做企业版？

| 角色 | 专业任务与交付 |
|---|---|
| 产品 | 区分客户需求、付费意愿和现有用户影响，给出目标客户与验证假设 |
| 技术 | 比较权限、多租户、迁移与持续维护方案，给出实现成本和分阶段路径 |
| 设计 | 分析管理员与成员流程，列出新增使用负担和关键交互 |
| 运营 | 评估销售、交付、支持工作量和团队承受能力，提出试点边界 |

可能的产出是完整企业版、小范围团队功能、暂缓三个选项的比较。若材料支持，可以推荐先做团队功能试点；若缺少客户证据，就保留结论并提出验证方案。这个例子不预设实际答案，也不限定项目只服务企业版或技术评审。

## 投入顺序与验收门槛

### 核心场景：Code Review

Code Review 与其他决策评审并列优先验证。输入包括需求或预期行为、base/head 或明确 diff、相关上下文、已运行的验证及已知约束。宿主给各角色提供实际代码与测试工具；模板自身不读取仓库或运行测试。

- 按改动选择正确性、架构与维护性、安全、测试与可靠性等角色；纯文案或简单改动可以缩减角色。
- 先各自检查实际代码，再围绕冲突或重叠的问题核实；审查未完成前不把“没发现问题”解释为安全证明。
- 每条问题包含文件/行或符号定位、触发条件、影响、证据或复现步骤、优先级与理由、修复建议及验证状态。推测问题明确标注待核实。
- 协调者按根因去重，区分阻塞问题、非阻塞建议和未验证部分，给出合并／修复后再审／材料不足的建议及理由。是否合并仍由用户或现有仓库规则决定。
- 验收关注经确认的有效问题、已知缺陷漏报、误报、重复率、审阅时间和成本；不用评论数量或投票比例评价质量。

在历史修复案例中可隐藏修复答案做回放；在真实 PR 中记录维护者采纳/拒绝的原因和后续结果。跨角色评审的收益需要与单助手及独立并行审阅比较，不预设多轮讨论更好。

### P0：可靠地完成一次真实评审

- 收敛 MCP 依赖兼容范围，安装可选依赖的 CI 必须验证实际入口与握手。
- 统一发言后的下一位通知，修复 Daemon 对忽略消息提前标记已读的问题。
- 修复订阅能力声明并验证双客户端消息到达；不以进程内单元测试替代联调。
- 让当前源码、安装说明与发布包能力一致，修正 adapter 自动执行等文档承诺。

验收：从干净环境开始，由宿主运行两个以上真实角色，走完开场、各自分析、冲突回应和决策说明；一个客户端重启后可恢复。运行失败、被跳过的功能和人工补救都记录。

2026-11-11 工程进展：依赖范围、真实入口握手、发言通知一致性、Daemon 消息确认和双客户端订阅均已补齐回归检查。`scripts/check_mcp_runtime.py` 使用真实 stdio/SSE 进程及固定测试发言，覆盖客户端重启，并用于干净 wheel 安装验证。它验证协议与状态恢复，不代表真实多模型评审或决策质量验收。使用方法及限制见 [可靠性说明](../TECHNICAL_RELIABILITY.md)。

### P1：验证专业协作的增益

- 从上述七类场景中按实际需求选取真实任务，填写通用及场景交付约定，记录缺席角色和重复、空泛的贡献。首批案例的选择不排除其余场景。
- 对角色和模型安排先保留人工配置，记录选择理由、费用和耗时（无法取得则标为未知）。
- 首轮与回应阶段按需要隔离上下文，检验角色是否补充了新的约束或选择。
- 验收最终材料包含方案代价、证据、未决问题和用户决策状态。

### P2：按使用结果决定产品形态

只在反复出现的手工工作上增加自动化：角色建议、材料准备、模型匹配、分歧追踪、结果回访。若流程模板已经足够，则保持轻量 Skill；独立服务必须证明它能减少跨工具组织和追溯成本。

暂缓扩大通用编排、纯人格视觉、直播/回放动效、发行渠道数量。已有 Viewer 可继续作为检查过程和结果的界面。

## 验证方法与维护决策

从维护者自身的真实决策开始，建议先积累 5–10 个案例。至少比较单助手深度分析与多角色协作；条件允许时，在相近材料和预算下增加独立多角色汇总、同模型多角色、异模型多角色对照，区分角色、交互和模型选择各自的贡献。

记录专业问题覆盖、经确认的新发现、可行方案增量、误报/重复意见、用户整理时间、总耗时与成本、最终采纳原因和后续结果。能做盲评时隐藏来源；短期无法确定正确性的决策，不用共识或信心提升代替实际结果。

- **继续投入**：多次真实任务出现可说明来源的专业增益，且使用者愿意再次主动使用。
- **调整形态**：价值主要来自角色任务和流程，现成宿主已足够承载，则收缩独立运行时维护。
- **降低维护或归档**：多次对照无可观察增益，或组织成本长期高于所得收益。

这些是验证标准，不是对成功的承诺。尚未推广和暂停开发本身不构成停止维护的证据。
