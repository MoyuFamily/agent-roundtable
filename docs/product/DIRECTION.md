# Roundtable 产品方向与近期计划

更新：2026-11-17。状态：优化方向已确认，优势与效果待真实使用验证。

本文定义当前产品方向、能力边界和投入顺序。早期 Sprint PRD、设计稿和发布讨论作为历史资料保留；涉及产品目标与优先级时，以本文为准。

## 定位与起点

**Roundtable 帮助用户把杂乱材料变成有依据、能取舍、可更新的决策建议。持续优化的两个重点是输入处理能力和输出质量。**

项目最初的需求是让不同角色协助做重要决策和评审，补足单一视角的局限；随后扩展到不同 Agent 和模型，以利用不同的能力、上下文和工具。项目开发后暂缓，未对外推广，因此不能把外部使用数据的缺失视为需求已被否定。

多角色、Agent 和模型是改善这两个结果的手段。是否增加角色、讨论轮次或模型，要看它能否纠正错误、发现遗漏、改进方案或降低用户整理负担。角色数量、讨论长度和报告外观本身不构成优势。

当前优先服务维护者自身及有类似需求的使用者。独立产品、可复用组件或轻量 Skill 的形态，由真实任务中的收益和维护成本决定。现有代码量不构成继续投入的理由，也不要求为了转型重写全部基础设施。

## 要实现的价值

“重要决策”指需要不同专业共同判断，且选择会影响资源投入、后续路径或返工成本的问题。当前场景清单见下表；验证顺序不缩小产品范围。普通事实查询和容易撤销的小选择不需要完整圆桌流程。该范围不代表项目具备覆盖所有专业领域的能力。

| 优化重点 | 用户应获得的价值 |
|---|---|
| 输入处理能力 | 从用户材料和必要的公共资料中提炼影响取舍的事实，保留来源、版本与适用条件，识别缺失和冲突，减少重复整理和解释 |
| 输出质量 | 快速看懂建议、依据、代价、改变判断的条件和下一步；需要时能核查细节，补充材料后能知道哪些结论发生了变化 |

输入处理的目标是形成可检查的决策依据，不以支持文件格式的数量衡量。输出质量同时包括内容正确性、取舍是否贴合用户目标、可行动性和阅读体验；图文报告是表达方式，不能替代证据质量。短答、详细报告、图表和导出应复用同一份已核对的事实、计算与结论，避免分别生成时相互矛盾。

这两项是要建设和验证的优势。当前没有足够对照证明本项目在这些方面领先；也不能把宿主临时完成的解析、核验或报告制作直接算作引擎已实现的能力。

## 场景清单

以下六类决策与 Code Review 都属于当前产品方向。Code Review 是并列的核心场景，不替代其他决策场景。角色组合是起点，应随问题、实际材料和可用能力调整。

| 场景 | 具体问题 | 可能需要的角色 | 应交付的结果 |
|---|---|---|---|
| 项目去留与方向 | 项目继续维护、转型，还是停止？ | 产品、技术、运营、资源规划 | 继续/调整/停止的比较、投入边界、验证计划和复审条件 |
| 产品范围与优先级 | 先做哪个用户群？哪些功能进入 MVP？ | 产品、设计、开发、运营 | 目标用户、MVP 范围、优先级依据、暂缓项和验收方式 |
| 技术路线 | 自研还是采购？继续现有架构还是迁移？ | 架构、开发、运维、产品 | 方案收益与总成本、依赖、迁移风险、演进和退出路径 |
| 发布与实施 | 当前版本能否上线？采用哪种迁移方案？ | 开发、测试、运维、用户支持 | 上线条件、阻塞项、实施步骤、回滚条件和未验证部分 |
| 资源与商业模式 | 有限预算投在哪里？免费、订阅还是按量收费？ | 产品、经营分析、技术、运营 | 资源分配或收费方案比较、成本/收入假设、敏感条件和试点指标 |
| 工作流程与工具选择 | 是否引入某个工具？收益是否抵得过迁移和维护成本？ | 实际使用者、技术、流程负责人 | 当前流程基线、工具收益、迁移/培训/维护负担和试用退出标准 |
| Code Review | 改动是否符合预期？有何缺陷或维护风险？是否建议合并？ | 正确性、架构与维护性、安全、测试与可靠性 | 带定位和证据的问题清单、阻塞项、未验证部分及合并建议 |

这些场景共用简报、角色任务、独立分析、交叉回应和综合取舍流程，分别约定所需材料与交付物。当前并没有七套已经验收的自动化产品：前六类可以通过通用 `decision-support` 流程调整角色和任务，产品/技术等也有既有模板；Code Review 另有专用模板。通用模板默认的产品、技术、设计、运营角色不应机械套用到资源分配或工具选择。

先选有真实问题和可取得材料的场景做验证，按实际收益安排投入。资源与商业模式需要明确成本、使用量、付费需求等假设；工具选择需要现有流程基线及试用证据。材料不足时标明未知，提出验证行动，不凭模型意见填补事实。

## 角色、Agent、模型的边界

| 对象 | 职责 | 当前安排 |
|---|---|---|
| 角色 | 定义关注问题、责任范围、需要的材料和交付物 | 用户或协调者选择；角色必须结合任务，不固定每次召集同一桌人 |
| Agent | 携带上下文和工具，执行角色任务并回应其他角色 | 由宿主创建或接入，明确实际可用材料和权限 |
| 模型 | 为具体分析任务提供推理与生成能力 | 宿主选择；记录选择理由和实际表现，不固化某品牌对应某职位 |
| 协调者 | 明确问题、组织角色、分配讨论重点、综合取舍 | 在宿主中执行，不代替专业角色编造独立意见 |
| 用户 | 提供目标、偏好与约束，作出最终决定 | 推荐方案与用户已批准的决定分别记录 |

多角色与多模型可以分别使用。只有一个模型时，仍可验证角色覆盖的价值；增加模型应有具体理由，并评估额外成本。先选择足以覆盖问题的角色，重复意见不增加权重；没有新增价值时减少后续调用或结束讨论。角色或模型名称本身不构成专业能力的证明。自动选人、自动模型路由和能力排行榜尚未实现。

## 建议的工作流程

1. **明确决策。** 整理待决定事项、目标、约束、偏好、备选方案、决策人和时间/成本预算。仅追问会影响取舍的信息；偏好未知时说明不同偏好下的选择，不默认最便宜或最保守。
2. **整理共同材料。** 主持人提炼决策相关事实，统一补充公共信息，记录来源位置、版本、适用条件与未核实项。检查影响选择的图表和页面；缺失、冲突与推算分别标明。敏感材料和产物留在授权的私有位置。
3. **安排必要的分析。** 给角色明确问题、材料和交付物，记录实际 Agent/模型及选择理由。各方使用同一版材料，可检查授权范围内的原文并质疑主持人的提炼。独立首轮由宿主分离上下文；提示词过滤不提供访问隔离。
4. **核实影响取舍的分歧。** 相关角色回应约束、提供替代方案；公共事实补查由主持人统一收集并更新共同简报。刷新各角色材料，重新考虑受影响判断，说明变化及原因。
5. **先交付简明结论。** 先说明建议、主要依据、代价、改变判断的条件和下一步，再按需要提供方案比较、证据与计算。正文和图文导出使用同一份核对结果。
6. **记录决定并支持复审。** 区分建议和用户确认；信息不足时交付验证计划。会中更新复用现有简报版本机制，已结束会议遇到新材料需发起后续评审。实施仍需符合用户授权。

阶段是协调者的工作约定，当前数据库仅管理轮次。根据问题覆盖程度、信息增益和预算决定是否继续；达到轮次上限可以结束并保留分歧。业务层会自动推进轮次，协调者不应每轮再次手动 advance。

## 最小交付约定

目标、角色任务等由协调者组织在 context 和发言中；共同证据与决策报告可使用持久化的 evidence/report，提供来源引用、简报版本校验及一致渲染。字段及示例见 [使用指南](../DECISION_WORKFLOW.md#保存共同证据与决策报告)。内容核验仍由宿主负责。

### 决策简报

- 待决定事项、决策人和时间。
- 目标、约束、偏好及其优先级，以及暂不讨论的范围；未确认的偏好标明未知。
- 备选方案，包括维持现状或暂缓（适用时）。
- 与决定相关的事实及来源 ID、页码/段落、版本和适用条件；计算保留输入与假设。
- 未核实、缺失、冲突的资料及其对选择的影响；必要的下一次补查。
- 可用 Agent、工具、模型及时间/费用预算。

### 角色任务

- 本角色的责任和边界。
- 必须回答的专业问题与可用材料。
- 预期交付物及需要其他角色回应的约束。
- 实际 Agent/模型安排与选择理由；没有观测到的配置不能猜测。

### 角色分析

- 专业判断与可行选项。
- 依据、来源和不确定性，区分事实、预测和偏好。
- 收益、成本、风险及与其他角色的冲突。
- 会改变判断的条件、待验证事项。
- 回应阶段引用相关发言 ID，说明新增或修订了什么。

### 最终决策说明

默认先给一页以内的决策概览，篇幅随问题调整，关键限制不能藏在附件里：

- 建议与决策状态：建议待用户决定／用户已确认／暂缓待验证。
- 主要依据及来源、相对于用户目标的取舍与代价。
- 最重要的反对理由、未知信息和会改变判断的条件。
- 下一步行动或验证；用户未确认的负责人只能标为建议。

详细层再给方案比较、资料定位、计算过程、角色覆盖和未验证部分。对结论有实质影响的主张须能回到原始资料，不能只引用角色意见。短答、表格、图表和导出共享事实版本、计算口径和推荐；更新时说明受影响结论、变化原因，以及旧产物是否已过期。

## 一个示例

问题：个人用户产品是否应该做企业版？

| 角色 | 专业任务与交付 |
|---|---|
| 产品 | 区分客户需求、付费意愿和现有用户影响，给出目标客户与验证假设 |
| 技术 | 比较权限、多租户、迁移与持续维护方案，给出实现成本和分阶段路径 |
| 设计 | 分析管理员与成员流程，列出新增使用负担和关键交互 |
| 运营 | 评估销售、交付、支持工作量和团队承受能力，提出试点边界 |

可能的产出是完整企业版、小范围团队功能、暂缓三个选项的比较。若材料支持，可以推荐先做团队功能试点；若缺少客户证据，就保留结论并提出验证方案。这个例子不预设实际答案，也不限定项目只服务企业版或技术评审。

## 投入顺序与验收门槛

### 核心场景：Code Review

Code Review 与其他决策评审并列优先验证。输入包括需求或预期行为、base/head 或明确 diff、相关上下文、已运行的验证及已知约束。宿主给各角色提供实际代码与测试工具；模板自身不读取仓库或运行测试。

- 按改动选择正确性、架构与维护性、安全、测试与可靠性等角色；纯文案或简单改动可以缩减角色。
- 先各自检查实际代码，再围绕冲突或重叠的问题核实；审查未完成前不把“没发现问题”解释为安全证明。
- 每条问题包含文件/行或符号定位、触发条件、影响、证据或复现步骤、优先级与理由、修复建议及验证状态。推测问题明确标注待核实。
- 协调者按根因去重，区分阻塞问题、非阻塞建议和未验证部分，给出合并／修复后再审／材料不足的建议及理由。是否合并仍由用户或现有仓库规则决定。
- 验收关注经确认的有效问题、已知缺陷漏报、误报、重复率、审阅时间和成本；不用评论数量或投票比例评价质量。

在历史修复案例中可隐藏修复答案做回放；在真实 PR 中记录维护者采纳/拒绝的原因和后续结果。跨角色评审的收益需要与单助手及独立并行审阅比较，不预设多轮讨论更好。

### 已有基础：可靠记录与恢复

依赖范围、真实入口握手、发言通知一致性、Daemon 消息确认和双客户端订阅已补齐回归检查。`scripts/check_mcp_runtime.py` 使用真实 stdio/SSE 进程及固定测试发言，覆盖客户端重启，并用于干净 wheel 安装验证。继续维护这些基础检查；它们验证协议与状态恢复，不代表输入处理或决策质量验收。使用方法及限制见 [可靠性说明](../TECHNICAL_RELIABILITY.md)。

### P0：打通材料到清晰建议的完整体验

- 从实际可取得的材料开始，提炼关键事实、对照原文、标明缺口，统一补充必要公共资料。先复用宿主解析工具，把重复且易错的手工环节作为自动化候选。
- 固定简明决策概览的交付约定；详细证据、计算和可选图文报告共用核对结果。报告样式不能掩盖未知信息。
- 将输入纠正、无可比数据、资料未读完整和隐私处理纳入真实任务验收。

验收：关键事实可定位，影响选择的缺口不被编造成事实；用户不用读会议记录即可理解建议、代价和下一步；摘要、正文与导出的关键数字和结论一致。记录用户补充说明、纠正错误及整理材料的负担，以及宿主人工补救，不用格式数量或报告篇幅代替效果。

首批实现：主持人提交结构化来源和证据条目，随简报版本保存并提供给各角色；报告按当前证据引用和版本校验后保存，统一生成结论 Markdown。Viewer 结论优先，内置读取和导出复用同一正文。该实现解决记录、引用与交付一致性；自动提炼、事实真伪和建议质量仍需宿主及真实使用验证。

第二批实现：本地文件提取为带页码/行号和读取状态的材料包，独立持久化原文，支持完整分页读取与搜索。导入与来源登记共同更新简报版本，证据引用校验实际片段及定位；报告显示提取缺口与核验说明。已完成合成材料及协议回归，真实材料的提炼效率和判断质量仍需使用验证。

### P1：让新信息能可靠改变结论

先用已有简报版本和历史记录执行更新：分发同一版材料，重审受影响判断，指出建议为何改变或仍成立，并标记过期产物。当前这些关联与重审由宿主负责；根据重复使用中暴露的遗漏，再决定是否增加证据与判断的结构化关联。

验收：在同一任务中更正一项会影响选择的事实，能够指出受影响判断和原结论，保留未变约束，给出一致的新结果；不能将新材料与旧结论无提示地混用。

### P2：用实际贡献决定角色和模型安排

2026-11-17 已完成一次真实源码快照审阅对照：一个独立完整审阅基线与三个独立专业角色、两轮回应。单助手发现了团队共同找到的四类功能问题，还额外指出撤销链接并发覆盖；团队主要补强测试和证据描述。该案例未做等预算或盲评，不支持宣称多角色更优。执行记录与后续取舍见 [Code Review 验收](CODE_REVIEW_ACCEPTANCE.md)。

- 从七类场景中按实际需求选任务，记录角色发现的有效错误、遗漏、约束和新方案，以及误报、重复和组织负担。首批案例不排除其他场景。
- 人工选择角色和模型，记录理由、费用与耗时（无法取得则标为未知）。独立分析和交叉回应按实际需要安排，不固定多轮。
- 在相近材料与预算下比较单助手、独立多角色汇总和交互评审。没有增益时减少参与者或停止后续调用；不能因为投入了更多角色就判定效果更好。

### 后续：按收益扩展输入与交付形式

只扩展真实任务中频繁需要、能减少整理或理解成本的材料格式与报告形式。优先复用已核对的数据，避免每种导出单独生成结论。若流程模板和宿主工具已经足够，则保持轻量 Skill；独立服务必须证明它能减少跨工具组织和追溯成本。

暂缓扩大通用编排、纯人格视觉、直播/回放动效、发行渠道数量。已有 Viewer 可继续作为检查过程和结果的界面。

## 验证方法与维护决策

从维护者自身的真实决策开始，建议先积累 5–10 个案例。至少比较单助手深度分析与多角色协作；条件允许时，在相近材料和预算下增加独立多角色汇总、同模型多角色、异模型多角色对照，区分角色、交互和模型选择各自的贡献。

| 维度 | 重点记录 |
|---|---|
| 输入处理 | 关键事实提取错误与遗漏、来源可定位性、冲突是否被发现、用户纠正与补充负担 |
| 输出质量 | 实质性错误、证据是否支持结论、取舍是否符合用户目标、下一步是否可执行、各产物是否一致 |
| 协作贡献与成本 | 经核实的新发现与方案、误报和重复、用户整理时间、总耗时与费用、实际采纳原因和后续结果 |

首批案例建立基线后再设置改进目标。能做盲评时隐藏来源；短期无法确定正确性的决策，不用共识、信心提升或外观评价代替实际结果。

- **继续投入**：多次真实任务在输入处理或输出质量上有可观察改善，整体收益值得付出时间与成本，且使用者愿意再次主动使用。
- **调整形态**：价值主要来自材料整理、角色任务或交付流程，现成宿主已足够承载，则收缩独立运行时或无增益的多角色调用。
- **降低维护或归档**：多次对照无可观察增益，或组织成本长期高于所得收益。

这些是验证标准，不是对成功的承诺。尚未推广和暂停开发本身不构成停止维护的证据。
