# WorkBuddy 付费 Skill 发布可行性评估

评估日期：2026-11-17。对象：将本仓库 Agent Roundtable 的能力产品化，在 WorkBuddy 开放平台尝试收费。本文是发布前评估；未登录开发者后台、未验证当前账号资格、未执行 WorkBuddy 实机测试或发布。

结论：建议做一个范围受控的付费试验。平台已具备原生收费渠道；当前需要验证的是 WorkBuddy 运行兼容性，以及目标用户是否愿意为明确的评审交付物付费。不能把“可上架”视为“已验证商业需求”。

## 平台条件：已确认与待确认

| 项目 | 截至评估日的依据与影响 |
| --- | --- |
| 收费入口 | WorkBuddy 开放平台“收入变现”支持付费技能、付费专家，支持一次性购买和按月付费；不必自行建设支付系统。[S1] |
| 入驻 | 支持个人和企业路径。个人认证目前要求中国大陆二代居民身份证、本人实名手机号等；不支持港澳台及外籍证件。资格需在自己的后台确认。[S2] |
| 免费与付费状态 | 官方文档明确发布后不能修改是否付费，当前不支持免费转付费。首个商业资产应从创建时规划为付费，不采用“同一资产先免费获客、以后切收费”的方案。[S1] |
| 退款与到账 | 买断和订阅均支持 7 天无理由退款；订单产生 30 天后可提现。销量、过退款期收入、可提现余额需要分别统计。[S1] |

| 手续费 | 官方公开文档确认平台服务费及微信支付手续费，但本次未找到官方公开的具体费率。社区文章提及内测平台费 1%，不能据此承诺长期费率或利润；签约页和实际账单优先。[S1][S8] |

WorkBuddy“技能市场”包含 SkillHub 来源，但收费入口在 WorkBuddy 开放平台。仓库现有 ClawHub/Hermes 发布流程不能直接代替 WorkBuddy 的资产创建、审核、定价和收款流程。[S1][S9]

## 当前仓库的发布差距

仓库已经实现会议、发言、简报修订、观点标注和 Markdown 输出。模型执行、证据核查与最终语义综合仍由宿主或协调者负责；这些边界在 [Skill 定义](../../src/skills/SKILL.md) 第 24–43 行已有明确说明。以下是静态审计结论，尚未经过 WorkBuddy 实机验收。

| 差距 | 仓库证据 | 首版处理建议 |
| --- | --- | --- |
| 上架元数据不齐 | [src/skills/SKILL.md](../../src/skills/SKILL.md) 第 1–17 行缺少 `display_name`、`display_name_en`、`description_zh`、`description_en`、`author`；官方将这些列为必填。[S3] | 新建 WorkBuddy 商品包，补齐中英文信息与真实示例。 |
| Skill 不是完整运行时 | Skill 第 38 行要求宿主通过已注册的 Roundtable 工具调用；[安装器](../../src/roundtable/skills/mcp-roundtable/install.py) 第 13 行列出的支持对象没有 WorkBuddy。 | 验证原生工具映射；首版避免强制买家自行安装 MCP。 |

[现有 Code Review 验收记录](CODE_REVIEW_ACCEPTANCE.md) 第 7 行明确说明：单助手找到了多角色共同发现的问题，还额外发现一个问题。该案例未做等预算控制和盲评；它证明协作记录可用，不能作为“多 Agent 更准确”的宣传依据。PRD 评审的付费价值需要单独验证。

项目当前 [LICENSE](../../LICENSE) 为 Apache-2.0。商业定位应建立在新增专项方法、交付与支持上；开源部分已有公开内容，云端加密不会使这部分内容变成独有资产。

## 产品选择

建议第一款商品：**Roundtable PRD 需求评审**。目标用户为已经有需求稿、即将交付开发的独立开发者、产品经理与小团队负责人。

输入一份 PRD 或需求描述，交付四份相互对应的结果：

1. 评审问题清单：标明原文位置、问题类别、严重程度与依据，区分事实、假设和待确认项。
2. 修改建议：给出可采用的需求补写内容，避免只有抽象批评。
3. 决策记录：列明建议、备选方案、反对意见，以及需要用户拍板的分歧。
4. 验收与行动清单：把确认的要求转成可检查的验收条件；负责人和日期由用户提供，缺失时留待确认。

首版限定支持文本及 Markdown，输出 Markdown 报告。文档/PDF 导出、跨会话历史、在线讨论直播、企业消息通知等，在首次验证付费需求后再按反馈增加。

WorkBuddy 已有原生专家团，包含主理人、独立成员调度和消息汇总机制。因此，“多个 AI 一起讨论”本身的差异有限。付费价值应由评审方法、证据定位、稳定交付和实际漏项发现能力来证明。[S4]

实现路径优先选择可独立运行的付费 Skill：适配已验证的 WorkBuddy 工具，保留 Roundtable 的评审流程、结构化结果与质量校验。若独立成员调度只在专家团形态可用，再评估专家团封装及其收费资格；收入变现文档只明确写了技能和专家，本文不推定专家团一定能收费。[S1][S4]

如实际只使用一个模型依次执行多种视角，需要如实描述为多视角评审，不能展示虚构的独立 Agent 发言记录。模型与工具可用性属于第一阶段验收内容。

## 付费试验方案

**建议首发 29 元一次性购买。** 这是验证付费意愿的试验价，不是已证实的市场均价。首版功能有限且不包含持续数据服务，买断比月订阅更容易解释其交付边界。若以后发展为持续托管服务，再单独评估订阅产品的实质服务差异与维护成本。

商品页明确说明支持的输入、输出示例、限制、反馈方式，以及 WorkBuddy 积分和可能产生的外部服务费用。付费资产使用权与模型算力费用分别说明，实际费用承担方式在真实调用后确认。[S5][S9]

试验分两个阶段，以下数量及阈值均为本项目建议，不是平台要求：

- 发布前：准备 10 份带已知缺陷的需求稿，覆盖正常输入、缺少关键条件、互相矛盾、长文本与中途失败。与相同模型条件下的 WorkBuddy 普通对话作对照，由人工核对发现的问题是否有原文依据。目标至少 9/10 能完整交付；任何虚构来源或伪造执行结果都需要修复。
- 发布后：运行 30 天，面向同一类目标用户展示真实样例和效果对比，争取至少 10 位真实买家。单独标记测试订单，不把自购、互购和礼貌购买作为需求证据。待订单经过 7 天退款窗口后，核对保留订单、退款原因、用户是否再次使用，以及售后耗时。

建议继续投入的初步信号：至少 10 位买家过退款期保留订单，退款率不高于 10%，至少 3 位用户在后续真实需求中再次使用，单笔平均人工支持不超过 10 分钟。小样本只支持继续试验，不能推导稳定转化率。

平台运营数据提供安装、调用、留存等指标，但安装不去重，技能文件被读取就会计为调用，不能据此推定完成任务或成交。销售依据收入账单，交付质量依据输出与真实反馈；曝光数据若后台没有提供，不自行编造转化率分母。[S10]

29 元 × 10 单为 290 元毛收入；29 元 × 100 单为 2,900 元毛收入。两者都未扣退款、平台和支付费用、税费、外部服务及人工维护成本。试验的首要目标是找到愿意付费且能自行使用的客户。

官方提供批量评测，当前公开说明为每日 10 次免费启动额度；可用于收集运行日志和效果数据，但不代替发布审核。[S6]

## 发布前需完成的验证

1. 账号路径：确认主体可认证、能开通收入变现；记录实际费率、结算条款、资产类目和收费设置。认证、人脸验证与微信签约由账号持有人完成。
2. 运行路径：在付费资产实际采用的云端环境中验证依赖安装、独立成员调用、工作目录写入、失败恢复和最终产物下载。测试时只使用非敏感样例。
3. 产品路径：证明固定评审流程比普通对话更稳定地发现有依据的问题，且用户无需安装、排障或配置额外服务即可完成首次任务。
4. 发布材料：完成中英文元数据、输入输出示例、功能范围、费用说明、反馈方式及可复现的效果对照。

在未确认运行能力前，开发工时仅作规划：限定范围的流程与模板适配 1.5–2.5 人日，平台兼容验证与修复 0.5–1 人日，样例评测和发布材料 2–2.5 人日，合计约 4–6 人日；不包含平台审核等待。若必须建设托管后端或长期运行的 MCP 服务，应另行估算，并先判断低客单价是否能承担维护成本。

## 信息边界

本次已核对官方公开文档及仓库静态实现，没有获取店铺交易数据或实际购买转化。2026-10-28 的开发者采访能佐证有人试卖、流量仍需自己验证，但不能证明该市场已有稳定盈利模型。[S7]

网上教程中“先免费发布再改付费”的说法与当前官方文档冲突，本文采用官方的不可转换规则。具体费率、审核时间、售价是否可修改、当前账号可用的收费资产类型，以及云端运行资源限制，仍需后台确认。
